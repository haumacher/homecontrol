# Internationalization

The device web UI speaks the language of the setting `ui.lang` (issue #24). The approach is the
phoneblock dongle's (`phoneblock-dongle/firmware/I18N-PLAN.md`, `main/i18n_sync.c`): a validated
language setting, key-based texts with the base language in the bundle, and language packs that a
release publishes next to its firmware on the update server, downloaded by the device into its
storage partition. The console and the log stay English (they are developer-facing).

## Pieces

| Where | What |
| --- | --- |
| `core/` `network_settings.h` | the setting `ui.lang`: `ui_lang_valid()`, `read_ui_lang()`, `store_ui_lang()` |
| `core/` `WebApi` | `ui.lang` in the settings whitelist (`GET`/`PUT /api/settings`), `lang` in `GET /api/auth/session`, the pack state as `i18n` in `GET /api/settings` |
| `core/` `LanguagePacks` | when to download the release's pack, the manifest, the SHA-256 check, the blob `i18n.<lang>.json.gz` (host-tested under the fake clock) |
| `platform/esp/components/hc_i18n` | `I18nService`: LanguagePacks over an `EspHttpFetcher` that exists only during a sync, the LittleFS blob store, the console command `lang` |
| `platform/esp/components/hc_web` | `/i18n/<lang>.json` from the blob store's directory |
| `web/ui/dist/i18n.js`, `web/ui/dist/lang/en.json` | the lookup `t(key)` and the English base table |
| `web/ui/lang/<code>.json` | the committed packs (German first), bundled into `storage.bin` by `gen_ui_image.py` |
| `scripts/i18n-pack.py` | key check, DeepL fill-in, the per-release manifest |
| `scripts/update-server.py` | serves the release's i18n directory next to the firmware on the desk |

## The setting

`ui.lang` is a language tag `[a-z]{2}(-[A-Z]{2})?` (`de`, `pt-BR`), default `en`: a charset that is
safe to splice into a URL and a file name. It is validated like `tz`, on every path that writes it
(the web API, the console's `lang set`) and on every read (an invalid stored value is logged and
replaced by `en`). The Settings page shows it as a selector of the bundled languages and the ones
the release's manifest offers, each by its own name (`Deutsch`), and applies a change at once. The
UI reads it at start from the open `GET /api/auth/session`, so the login page is localized too.
Any well-formed tag is accepted, also one no pack exists for yet: the UI then stays English and
says so under the selector. A regional tag falls back to its base language: `de-AT` layers the
bundled `de-AT` pack (if any) and the downloaded one over the bundled `de`, and the device
downloads the release's `de-AT` pack when it has one, else its `de` pack (stored under the device's
own tag, `i18n.de-AT.json.gz`, so `/i18n/de-AT.json` serves it); `en-GB` is built in like `en`.

## The base language: English, in the bundle

The author's language is German, the code, the docs and the API's reasons are English; English is
the base. `web/ui/dist/lang/en.json` holds every key (310); `i18n.js` loads it before the first
render (a module-level `await`), so it is the offline fallback for every key a pack lacks. It is
part of the UI bundle (LittleFS image), not compiled into the firmware. Rejected: the base inline
in `i18n.js` (two sources of the key set for the scripts and the tests to keep apart), and German
as the base (the API's reasons are English and show for codes the table does not know).

## Language packs

A pack is a flat JSON object of the base's keys to strings, with the base's `{placeholders}`, plus
`lang.name`, the language's own name. Two sources, merged key by key (`setLanguage()` in
`i18n.js`):

1. **Bundled**: `web/ui/lang/<code>.json`, committed, copied into the UI image
   (`ui/lang/<code>.json.gz`, about 5 KB per language) and, on the host, into `web/ui/dist/lang/`
   by the POSIX build (the copies are not versioned). A device works offline in every language its
   UI image carries. German is the first.
2. **Downloaded**: the pack of `ui.lang` that the release published on the update server after the
   firmware was built (a new language, corrected strings). The device stores it and serves it at
   `/i18n/<code>.json`; its keys win over the bundled pack's.

A pack is untrusted input (the manifest is not signed, see below): `i18n.js` takes only string
values, and the UI sets them only as `textContent` or attribute values; nothing from a pack is
parsed as HTML. A pack string `<img src=x onerror=...>` shows as those characters (checked with
Playwright against the POSIX server, a routed `/i18n/de.json` with `<script>`, `<img onerror>` and
`<b>` strings: no element was created, no script ran).

## The download (`LanguagePacks`)

Each release publishes its own bundle next to its firmware:
`<update.url>/<version>/i18n/manifest.json` (the version without build metadata, `0.1.0-dev`
for a development build):

```json
{"version": "0.2.0",
 "packs": {"de": {"name": "Deutsch", "path": "lang-de.json.gz",
                  "sha256": "<64 hex digits>", "size": 5035}}}
```

The pack files are the gzip-compressed JSON the browser loads (served as stored, with
`Content-Encoding: gzip`, so the device never decompresses). The core decides when:

- a pass runs 20 s after the start (every boot, so an OTA update brings the new release's pack and
  the device learns the offered languages) and 0.5 s after `ui.lang` changed (a fetch in flight is
  discarded when it returns);
- it needs the network up, the wall clock synchronized (TLS checks certificate dates) and
  `update.url`; while one is missing it waits, polling every 30 s, and the state names the reason
  (logged when it changes);
- English: nothing to download, stored packs are removed; a language the manifest does not offer:
  `not_offered`, stored packs are removed (a pack of an older release must not shadow the new UI's
  bundled one); a stored pack with the manifest's SHA-256: `installed`, nothing fetched;
- otherwise the pack is fetched and **streamed** into the blob `i18n.<lang>.json.gz` (issue #43):
  the fetcher hands the body over in pieces of at most 2 KB, `LanguagePacks` hashes each piece and
  appends it to a `BlobWriter` (a temporary file the readers do not see), and only a pack whose
  length and SHA-256 match the manifest replaces the stored one (atomic rename); every other
  `i18n.*` blob is then removed: one pack lives on the device. No pack is ever held in RAM as a
  whole, so its size is bounded by the storage, not by a buffer (the earlier limit of 12288 bytes,
  the old fetch buffer, is gone). Refused, each with the limit that applied in the reason: a pack
  the manifest announces larger than the blob store's free space (before the fetch: "pack <url>
  refused: 40960 bytes, the blob store has 10000 bytes free"), a server that announces another
  length than the manifest, a body that grows past the manifest's size (at the piece that crosses
  it), a short body or a hash mismatch (at the end), a store that fills up during the stream ("cannot
  store the pack <url> after 4096 bytes: no space"). Each refusal discards the temporary blob and
  keeps the stored pack;
- a failure (fetch, HTTP status, malformed manifest, a manifest of another release, a size or
  hash mismatch, the store) is logged and retried after 1, 2, 4, ... minutes up to an hour; the
  previous pack stays. A malformed manifest entry (a code that is not a tag, a path with a
  directory, a bad checksum or size) is refused alone with a log line; if it is the wanted
  language's entry the pass fails with that reason. There is no periodic re-sync: a release's
  bundle changes only with a new firmware version.

The manifest is **not signed**, unlike an OTA image: the strings are display text, the SHA-256
protects against a truncated or corrupted transfer, HTTPS with the certificate bundle is the
transport trust, and a hostile server achieves at worst wrong text, which the UI renders as text.
The dongle made the same trade so that publishing a bundle for an unreleased build needs no release
key.

**Storage**: the blob store (`LittleFsBlobStore`, `/storage/state/i18n.<lang>.json.gz`), not a
separate directory: its write is an atomic replace (temporary file, rename), names are validated,
it has a host implementation and a fake for the tests, and the core already uses it. The web
server reads the file directly from the blob store's directory in its own task (LittleFS serializes
the access; the rename makes a reader see the old or the new pack). The name prefix `i18n.` keeps
it apart from the value store (`v.`), the history (`h.`) and the image (`image.`).

**Memory on the C6**: the `LanguagePacks` object and the fetcher wrapper are about 2 KB of .bss;
during a sync the manifest's 4 KB buffer (`kMaxManifest`, the manifest is parsed as a whole) and
the `EspHttpFetcher` (about 3 KB with its 2 KB piece buffer) are on the heap, freed after the
manifest and 2 s after the last fetch; the worker task (8 KB stack) lives only during a fetch. A
pack download needs no more RAM than a manifest fetch, whatever the pack's size.

**Console**: `lang status` (ui.lang, the pack state and its reason, the release directory, the
offered languages), `lang set <code>` (validated, starts the sync), `lang sync` (a pass now).
`settings list` shows `ui.lang` with the other stored settings.

**POSIX**: the same `LanguagePacks` over the POSIX HTTP fetcher and the file blob store (the pack
lands in the blob directory beside the settings); the host web server serves `/i18n/<lang>.json`
from that store, 204 No Content without a pack. Tested on the desk against `scripts/update-server.py`
(manifest, pack, hash, up-to-date on the second pass, `not_offered` for `fr`).

## What is translated, what is not

- Translated: every text of the web UI (titles, labels, buttons, hints, aria labels, the refusal
  texts the UI composes, the API's error codes it knows), and number and date formats follow the
  UI language.
- Not translated: units (`°C`, `%`, `KB`, `min`, `s`); the datapoint, function and room labels,
  which come from the runtime image (E-Home engineers them, possibly in several languages: the UI
  picks the label of the UI language, then the browser's, then English); the device's reasons
  that accompany a state (`waiting: the network is down`) and the English reason of an API code the
  table does not know; the console and the log.

## Adding a language

1. `scripts/i18n-pack.py translate --lang fr` creates `web/ui/lang/fr.json`: with `DEEPL_AUTH_KEY`
   set (a DeepL API key; a key ending in `:fx` uses the free API) it machine-translates every
   key, placeholders protected; without it, it lists the missing keys and exits 1. Set
   `lang.name` to the language's own name. Review the strings (product register; the German pack
   uses "Du", as the author's other UIs do).
2. Add the code and its name to `bundled` in `web/ui/dist/i18n.js` if the pack ships in the UI
   image (the key-set test checks that every committed pack is listed).
3. `scripts/i18n-pack.py check` must pass (no missing, extra or broken keys); so must the host
   test `Lang: every committed pack has exactly the keys and placeholders of the English base`.

A language that ships after a release goes into the release's i18n directory only: the device
offers it in the selector once it has read the manifest.

When a UI change adds keys: add them to `en.json`, then `scripts/i18n-pack.py translate` fills
the packs through DeepL (or by hand), reviewed and committed with the change. Nothing is translated
at release time.

## Releasing

`scripts/i18n-pack.py manifest <release dir> --version <hc::kVersion>` writes
`<release dir>/i18n/lang-<code>.json.gz` and `manifest.json` from the committed packs; it refuses a
pack that fails the check, and warns about a pack above 32 KB compressed (`WARN_PACK`: every device
downloads it after each update; the device itself takes any pack its storage has room for). The release directory is
`<update.url>/<version>` on the update server. On the desk, `scripts/update-server.py` does this for
the build it serves (`<base>/<version>/i18n/`), so `update url set http://<desk>:8070` and
`lang sync` exercise the download.

- The OTA update replaces the application, not the UI image (doc/web.md, "Gap"): after an OTA
  update without a new `storage.bin` the old UI runs with the new release's downloaded pack; keys
  the old UI uses and the new pack no longer has fall back to the old bundled pack, then English.
